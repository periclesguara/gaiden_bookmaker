4. AUDITORIA INICIAL OBRIGATÓRIA
--------------------------------

Executar primeiro, sem modificar arquivos:

    git rev-parse --show-toplevel
    git status --short --branch
    git remote -v
    git branch -vv
    git worktree list

Atualizar somente as referências remotas:

    git fetch --all --prune

Recalcular a divergência da branch atual:

    git rev-list --left-right --count '@{upstream}...HEAD'

Listar hashes locais ausentes de todos os remotes:

    git log --branches --not --remotes \
      --date=short \
      --pretty=format:'%H%x09%ad%x09%an%x09%s'

Listar branches locais com hashes ausentes dos remotes:

    git for-each-ref refs/heads --format='%(refname:short)' | \
    while IFS= read -r branch; do
      count=$(git rev-list --count "$branch" --not --remotes)
      if [ "$count" -gt 0 ]; then
        printf '%s\t%s\n' "$count" "$branch"
      fi
    done

IMPORTANTE: a lista acima ainda pode conter commits que já chegaram ao GitHub
com outro hash. Antes de afirmar que uma alteração é inédita, comparar patch-id
ou usar git cherry contra o upstream correto:

    git cherry -v origin/main main
    git cherry -v origin/feature/translate-2025 feature/translate-2025

Interpretação de git cherry:

    +  patch ainda não encontrado no upstream comparado
    -  patch equivalente já existe no upstream com outro hash

Quando houver várias branches remotas, comparar patch-id contra refs/remotes/*
antes de classificar um commit como não publicado.

7. ESTRATÉGIA OBRIGATÓRIA DE ISOLAMENTO
---------------------------------------

Como o worktree principal está sujo, toda integração deve acontecer em um novo
worktree criado a partir do remote atualizado.

Exemplo para revisão, usando um nome ainda inexistente:

    git fetch origin --prune
    git worktree add ../gaiden_bookmaker_review \
      -b review/local-commits-v1 origin/main

Antes de criar:

    git branch --list review/local-commits-v1
    git worktree list
    test ! -e ../gaiden_bookmaker_review

Se branch ou diretório já existir, escolher outro nome. Nunca reutilizar um
worktree sem auditar seu estado.

Dentro do novo worktree:

    git status --short --branch
    git rev-parse --abbrev-ref HEAD

O resultado deve estar limpo antes de cherry-pick, edição ou teste.


8. COMO TRANSPORTAR COMMITS ANTIGOS
----------------------------------

Não fazer merge de branches antigas e divergentes. Preferir revisão commit a
commit ou extração manual de partes ainda válidas.

Inspeção:

    git show --stat --summary <commit>
    git show --name-status <commit>
    git show --check <commit>
    git diff origin/main...<branch> -- <caminho>

Para um commit pequeno e aprovado:

    git cherry-pick --no-commit <commit>
    git status --short
    git diff --check
    git diff

Usar --no-commit permite revisar e remover trechos obsoletos antes de criar um
novo commit. Não continuar se houver conflito não compreendido.

Para commits grandes ou contaminados por dados:

    git show <commit>:<caminho> > /tmp/arquivo_para_inspecao

Depois, implementar somente o comportamento necessário no código atual. Não
copiar cegamente árvores completas de uma versão antiga.


9. RESOLUÇÃO SEGURA DE CONFLITOS
--------------------------------

Quando houver conflito:

1. Parar e listar:

       git status --short
       git diff --name-only --diff-filter=U

2. Para cada arquivo, comparar:

       git diff --base -- <arquivo>
       git diff --ours -- <arquivo>
       git diff --theirs -- <arquivo>

3. Entender a intenção do código atual e do commit antigo.
4. Aplicar resolução mínima com edição explícita.
5. Executar testes específicos do componente.
6. Revisar o diff completo antes de marcar como resolvido.

Não usar para resolver arquivo inteiro:

    git checkout --ours <arquivo>
    git checkout --theirs <arquivo>

Esses comandos somente podem ser usados após revisão comprovada e para um alvo
exato, nunca como atalho global.

Se o conflito envolver alterações locais do usuário, interromper e pedir
orientação. Não presumir qual versão deve prevalecer.


10. REGRAS DE STAGING
---------------------

Sempre adicionar caminhos explícitos:

    git add -- path/to/file_a.py path/to/file_b.html

Para partes específicas:

    git add -p -- path/to/file.py

Antes de commitar:

    git status --short
    git diff --check
    git diff --cached --check
    git diff --cached --stat
    git diff --cached --name-status
    git diff --cached

Cancelar o commit se houver arquivo inesperado, binário, dado editorial, banco,
segredo, log, build ou artefato gerado.

14. REGRAS PARA CRIAR COMMITS
-----------------------------

Cada commit deve ter uma única responsabilidade. Separar, quando aplicável:

1. migrations/models;
2. serviços e regras de domínio;
3. views/URLs;
4. templates/UI;
5. testes;
6. documentação;
7. limpeza de .gitignore.

Formato recomendado:

    feat(pipeline): descrição objetiva
    fix(editorial): descrição objetiva
    test(pipeline): descrição objetiva
    docs(git): descrição objetiva
    chore(repo): descrição objetiva

Antes do commit final:

    git diff --cached --stat
    git diff --cached
    git status --short

Criar commit não autoriza push.


15. REGRAS PARA SINCRONIZAR COM O GITHUB
----------------------------------------

Antes de publicar uma branch de revisão:

    git fetch origin --prune
    git rev-list --left-right --count origin/main...HEAD
    git log --oneline --decorate origin/main..HEAD
    git diff --stat origin/main...HEAD

Se origin/main avançou, integrar somente no worktree limpo. Preferir rebase da
branch de revisão antes do push inicial, nunca da branch suja do usuário:

    git rebase origin/main

Se a branch já estiver publicada e o rebase exigir force push, parar e pedir
autorização. Não usar force por padrão.

Push somente após autorização explícita:

    git push -u origin review/local-commits-v1

Não fazer:

    git push origin main

Após push, abrir Pull Request em modo draft e informar:

- commits incluídos;
- commits descartados e motivo;
- testes executados;
- riscos conhecidos;
- migrations;
- impacto em dados e compatibilidade;
- ausência de artefatos e segredos.

17. CRITÉRIOS DE PARADA
-----------------------

Parar e pedir orientação se ocorrer qualquer situação abaixo:

- arquivo em conflito também está modificado no worktree principal;
- migration local conflita com migration publicada;
- teste exige credencial, custo externo ou alteração de produção;
- segredo aparece em histórico ou staging;
- commit contém grande volume de data/, backups ou artefatos;
- não é possível determinar se uma alteração antiga ainda é válida;
- push exigiria force;
- branch remota foi alterada durante a revisão;
- testes relevantes falham por causa não compreendida;
- o escopo necessário é materialmente maior que o autorizado.
